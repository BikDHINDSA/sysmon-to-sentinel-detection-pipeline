# Phase 4: Incident Investigation & Reporting

This phase covers the incidents generated by Phase 3's analytics rules, closing the loop from raw telemetry through to an investigated, documented security incident — the deliverable a SOC analyst would actually produce at the end of a shift.

## Incident Volume Summary

Following the Phase 2 attack simulation (including the re-run of each stage after rules were made live, per Phase 3's verification approach), Sentinel generated **21 incidents** across all four analytics rules.

| Rule | Incidents Generated | Severity |
| :--- | :--- | :--- |
| Registry Run Key Persistence | 5 | High |
| Scheduled Task Creation | 8 | Medium |
| Suspicious Powershell Download Cradle | 4 | High |
| Discovery Command Sequence | 2 | Medium |
| **Total** | **21** | — |

Each incident maps 1:1 to a single triggering alert (Active alerts: 1/1 across all incidents), consistent with the rules' "trigger an alert for each event" grouping configuration rather than correlating multiple alerts into a single incident.

## Why incident count exceeds rule count

Four rules produced 21 incidents rather than 4 because each stage of the attack chain was executed multiple times over the course of the project — during initial telemetry validation in Phase 2, and again deliberately after each rule was made live in Phase 3, to confirm automatic incident generation rather than relying on manual query results alone. The incident volume is therefore a byproduct of iterative testing, not a reflection of the attack chain itself being repeated 21 times in a single simulated intrusion.

## Sample Incident Walkthrough

To demonstrate the investigation workflow end-to-end, one incident was opened and worked through in full, from initial alert to disposition.

**Incident:** Suspicious Powershell Download Cradle
**Severity:** High
**Category:** Command and Control
**MITRE ATT&CK:** T1059.001 (Execution), T1071 (Command and Control)


### Investigation notes

- **Entities involved:** target host (`vm-soc-target`), account (`labadmin`), the flagged process command line containing `DownloadString` and `IEX`
- **Timeline:** alert fired within the rule's 5-minute scheduled query window following execution of `stage1-download-cradle.ps1`
- **Cross-referencing:** the same activity was independently confirmed via the parallel Sysmon-based query (Rule 1's second detection path), corroborating the finding across two telemetry sources rather than relying on a single log
- **Disposition:** True Positive — expected activity, generated by the controlled attack simulation in Phase 2. In a real environment, this pattern would warrant immediate isolation of the host and review of the parent process chain to identify the initial access vector.

### Why this incident was chosen for the walkthrough

The download cradle detection was selected as the representative example because it involves the clearest attacker-relevant signal (a live command-and-control-style execution pattern) and because it was the technique validated against two independent telemetry sources, making it the strongest single example of this project's dual-source detection design.

## Investigation Workflow Applied

For each incident type, the same triage approach was used:

1. Open the incident and review the entity list (account, host, process)
2. Cross-reference the triggering alert's timestamp against the corresponding attack stage's execution time
3. Where a parallel detection source existed (Rules 1 and 3), confirm the same activity was independently flagged
4. Classify disposition (True Positive, given this is a controlled simulation) and document reasoning
5. Note what a real-world response action would be, even though no automated or manual containment action was taken against this lab VM

## Phase 4 Completion Criteria

**Phase 4 is considered complete when:**

1. All incidents generated by Phase 3's rules have been reviewed and their volume accounted for.
2. At least one incident has been fully investigated and documented as a representative walkthrough.
3. Each investigated incident's disposition is stated with supporting reasoning.
4. The investigation workflow applied is documented clearly enough to be repeatable against a new incident.
